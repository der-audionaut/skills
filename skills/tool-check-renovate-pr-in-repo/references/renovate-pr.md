# Renovate-PRs

Woran man einen Renovate-PR erkennt, wie er aufgebaut ist, welche Arten es gibt und welche davon `tool-dep-update-check` prüfen kann — dazu die `gh`-Befehle, mit denen der Skill liest und schreibt, und die zwei Regelwerke, die jede Entscheidung über Push und Approve tragen: was Renovate mit einem Branch tut, den jemand anderes angefasst hat, und wann GitHub eine Approval zählt. Jede Aussage über Verhalten trägt ihre Quelle; die Vorlagen für Branch und Titel stammen aus Renovates Quelldatei der Optionen (`lib/config/options/index.ts` auf `main`, Stand Oktober 2026), weil die Doku dieselben Werte nur verteilt über eine sehr lange Seite zeigt.

---

## A — Erkennung

**Der Autor.** Das Mend-Renovate-GitHub-App-Konto erscheint in PR-Listen als `renovate[bot]`; GitHub-Suchen filtern App-Konten mit `author:app/<name>`, also `author:app/renovate` — die Suchdoku beschreibt den Qualifier als „finds issues and pull requests created by a certain user or integration account" und gibt `author:app/robot` als Form für Integrationskonten an (https://docs.github.com/en/search-github/searching-on-github/searching-issues-and-pull-requests). Ein selbst gehostetes Renovate läuft unter irgendeinem Konto, oft einem technischen Nutzer ohne `[bot]`-Suffix; dann greift der Autorfilter nicht, und die zweite Erkennung trägt allein.

**Der Branch.** Jeder Renovate-Branch beginnt mit `branchPrefix`, Standard `renovate/`, „Prefix to use for all branch names" (https://docs.renovatebot.com/configuration-options/#branchprefix). Dahinter kommt `branchTopic`, standardmäßig `{{{depNameSanitized}}}-{{{newMajor}}}` plus `.x`, bei getrennten Patches mit Minor dazwischen, und bei einem reinen Lock-Update der Zusatz `-lockfile` (https://docs.renovatebot.com/configuration-options/#branchtopic). So entstehen `renovate/lodash-4.x`, `renovate/lodash-4.x-lockfile`, bei Gruppen `renovate/<groupSlug>` (`group.branchTopic` ist `{{{groupSlug}}}`), bei Lockfile-Maintenance `renovate/lock-file-maintenance`, bei Docker-Digest-Pins `renovate/digests-pin`, bei Rollbacks `…-rollback`, bei Ersetzungen `…-replacement` und bei Sicherheits-PRs `renovate/<datasource>-<dep>-vulnerability`. Wer den Präfix geändert hat, hat das in der Renovate-Konfiguration des Repos getan — sie liegt in `renovate.json`, `renovate.jsonc`, `renovate.json5`, `.github/renovate.json`, `.github/renovate.jsonc`, `.github/renovate.json5`, `.gitlab/renovate.json`, `.gitlab/renovate.jsonc`, `.gitlab/renovate.json5`, `.renovaterc`, `.renovaterc.json`, `.renovaterc.jsonc`, `.renovaterc.json5` oder `package.json` (dort unter dem Schlüssel `renovate`) — so die Liste `configFileNames` in Renovates Quellcode (https://github.com/renovatebot/renovate/blob/main/lib/config/app-strings.ts); die Doku sagt dazu nur, dass `renovate.json` der Standard ist und bei mehreren Dateien die erste gefundene gilt (https://docs.renovatebot.com/config-overview/). Die Datei einmal lesen, `branchPrefix` und `additionalBranchPrefix` herausziehen, sonst `renovate/` annehmen.

**Warum beides.** Renovate selbst benutzt Branchname und PR-Titel „like a cache key" (https://docs.renovatebot.com/key-concepts/pull-requests/): Ein PR gehört zu Renovate, wenn Branch und Titel zu seinen Vorlagen passen. Die Vereinigung aus Autorfilter und Branchpräfix findet beide Betriebsarten — App und selbst gehostet —, und ein PR, der nur über das Präfix gefunden wurde, bekommt im Bericht den Hinweis, dass der Autor nicht das Renovate-App-Konto ist.

## B — Anatomie

**Der Titel** ist die Commit-Botschaft des Branchs und setzt sich aus drei Vorlagen zusammen (https://docs.renovatebot.com/configuration-options/#commitmessageaction, `#commitmessagetopic`, `#commitmessageextra`): `commitMessageAction` (Standard `Update`), `commitMessageTopic` (Standard `dependency {{depName}}`) und `commitMessageExtra` (Standard `to <Version>` — bei Majors nur die Major-Nummer, bei Digests der Kurz-Digest). Daraus:

- `Update dependency lodash to v4.17.21` — ein Paket, eine Version.
- `Update dependency lodash to v5` — ein Major; die Doku warnt, dass Titel ohne volle Version wie `Update react (major)` mehrere Updates meinen können (https://docs.renovatebot.com/key-concepts/pull-requests/).
- `chore(deps): update dependency lodash to v4.17.21` — mit `semanticCommits` (Standard `auto`: an, wenn die Historie des Repos konventionelle Commits zeigt, https://docs.renovatebot.com/configuration-options/#semanticcommits), Typ `chore`, Scope `deps`, und `commitMessageLowerCase` `auto` schreibt den Rest klein.
- `Update all non-major dependencies` oder ein anderer `groupName` — ein Gruppen-PR; `group.commitMessageTopic` ist `{{{groupName}}}`.
- `Lock file maintenance` — `lockFileMaintenance.commitMessageAction`, ohne Topic und Extra.
- `Pin dependencies` — `pin.commitMessageAction` `Pin` mit Topic `dependencies`, Gruppe `Pin Dependencies`.
- `Update node Docker tag to v22` und `Update node:22 Docker digest to abc1234` — die Docker-Datasource setzt `commitMessageTopic` auf `{{{depName}}} Docker tag` beziehungsweise `… Docker digest` (https://github.com/renovatebot/renovate/blob/main/lib/modules/datasource/docker/index.ts); `Pin Docker digests` ist die Pin-Gruppe.
- `Roll back dependency lodash to v4.17.20`, `Replace dependency request with …`, `Update dependency lodash to v4.17.21 [SECURITY]` — Rollback, Ersetzung, Sicherheits-PR (Suffix aus `vulnerabilityAlerts.commitMessageSuffix`).

GitHub-Actions-Updates tragen den generischen Topic — der Manager bringt keine eigene Titelvorlage mit (https://github.com/renovatebot/renovate/blob/main/lib/modules/manager/github-actions/index.ts) —, solange kein Preset ihn überschreibt; verlass dich bei ihnen nicht auf den Titel, sondern auf die geänderten Dateien unter `.github/workflows/` (Abschnitt C).

**Der Body** wird aus festen Bausteinen in fester Reihenfolge gebaut (https://github.com/renovatebot/renovate/blob/main/lib/workers/repository/update/pr/body/index.ts): Kopf, Update-Tabelle, Notizen, Release Notes, Konfigurationsbeschreibung, Steuerelemente, Fußzeile. Was der Skill braucht:

- **Die Tabelle** beginnt mit der Zeile `This PR contains the following updates:` und hat eine Zeile je Update; die Spalten sind `prBodyColumns`, Standard `Package`, `Type`, `Update`, `Change`, `Pending`, leere Spalten entfallen (https://docs.renovatebot.com/configuration-options/#prbodycolumns). Die Spalte `Change` ist als `` `{{{displayFrom}}}` → `{{{displayTo}}}` `` definiert (https://docs.renovatebot.com/configuration-options/#prbodydefinitions) — mit dem Pfeil `→` (U+2192); ältere Renovate-Versionen und viele noch offene PRs schreiben `->`. Wer die Zeilen per Grep aus dem Body zieht, sucht nach beidem. Bei Lockfile-Maintenance steht in `Change` nur `All locks refreshed`. Die Spalten `Age`, `Adoption`, `Passing` und `Confidence` sind optionale Definitionen mit Mend-Badges, die manche Konfigurationen einschalten.
- **Die Release Notes** stehen eingeklappt unter der Tabelle, weil `fetchChangeLogs` standardmäßig `pr` ist (https://docs.renovatebot.com/configuration-options/#fetchchangelogs). Sie machen den Body groß — zehn bis fünfzig Kilobyte sind normal — und sind für den Skill nicht die Quelle: Changelogs liest `tool-dep-update-check` selbst und vollständig.
- **Die Rebase-Checkbox** ist die Zeile `- [ ] <!-- rebase-check -->If you want to rebase/retry this PR, check this box` (https://github.com/renovatebot/renovate/blob/main/lib/workers/repository/update/pr/body/controls.ts). Sie ist das Steuerelement, das Renovate den Branch neu bauen lässt — und das jeden fremden Commit verwirft, siehe Abschnitt E.
- **Der Hinweis „Immortal"** (`This PR will be recreated if closed unmerged`) steht bei PRs, die Renovate nach dem Schließen neu anlegt (https://docs.renovatebot.com/key-concepts/pull-requests/). Für die Prüfung ist er ohne Belang; er erklärt nur, warum Schließen keine Lösung ist.

## C — PR-Arten und Prüfbarkeit

`tool-dep-update-check` prüft genau ein Paar: ein Paket, eine Ausgangs- und eine Zielversion, in einem Ökosystem, das seine Referenz kennt (npm, Composer, Maven, Gradle, pip und Verwandte, Cargo, Go, Bundler, NuGet — `skills/tool-dep-update-check/references/oekosysteme.md`). Maßgeblich ist nicht der Titel, sondern der Diff des PR-Branchs gegen seine Basis, beschränkt auf Manifest- und Lock-Dateien; die Body-Tabelle ist die Gegenprobe.

- **Ein Paket, Manifest und Lock geändert** — prüfbar. Das Paar steht im Manifest-Diff; die Tabellenzeile muss dasselbe sagen.
- **Ein Paket, nur Lock geändert** (Branch mit `-lockfile`, Abschnitt A) — prüfbar. Das Ziel liegt im bestehenden Constraint; `tool-dep-update-check` nennt das in seinem Bericht ein reines Lock-Update (`skills/tool-dep-update-check/SKILL.md`, Abschnitt 2, „Constraint gegen Lock"). Das Paar kommt aus dem Lock-Diff.
- **Gruppen-PR** — prüfbar, je Zeile der Tabelle ein Paar, jedes einzeln. Freigegeben werden kann der PR nur, wenn jedes Paar möglich ist; die Gruppe zu teilen ist Renovate-Konfiguration (`groupName`, `separateMinorPatch`), nicht Sache des Skills.
- **Lockfile-Maintenance** — nicht prüfbar. Alle Locks werden aufgefrischt, es gibt kein Paar, und die Zahl der bewegten Pakete ist beliebig. Übersprungen, mit Grund.
- **Pin-PR** — nicht prüfbar, weil nichts zu prüfen ist: Das Manifest wechselt von einem Bereich auf die Version, die der Lock schon hält; Ausgang und Ziel sind gleich. Übersprungen, mit Grund — die Entscheidung, ob das Projekt pinnen will, ist Konfiguration.
- **Docker-Tag, Docker-Digest, Digest-Pin** — nicht prüfbar: kein Ökosystem der Prüfung, und der Probelauf des Prüf-Skills (Install, Build, Tests) sagt über ein Basisimage nichts. Übersprungen.
- **GitHub-Actions** (Dateien unter `.github/workflows/`, Versions- oder Digest-Update einer Action) — nicht prüfbar, aus demselben Grund. Übersprungen.
- **Rollback** — nicht prüfbar: ein Downgrade, bei dem `tool-dep-update-check` nachfragt, ob es so gemeint ist (`skills/tool-dep-update-check/SKILL.md`, Abschnitt 1). Übersprungen, mit dem Hinweis, dass ein Rollback eine andere Aufgabe ist.
- **Ersetzung** (`Replace dependency …`) — nicht prüfbar: ein anderes Paket, kein Versionssprung. Übersprungen.
- **Sicherheits-PR** (`[SECURITY]`) — prüfbar wie ein normaler Paket-PR; der Zusatz ändert nichts an Paar und Diff. Was den Alert selbst angeht — ob die Zielversion ihn schließt —, ist Sache des Team-Skills `update-packages`, nicht dieses.

Ein PR, dessen Manifest-Diff und Tabelle sich widersprechen — anderes Paket, andere Version —, ist nicht prüfbar und wird so gemeldet; raten, welche Seite stimmt, ist keine Prüfung.

## D — Die `gh`-Befehle

Alle Befehle brauchen ein angemeldetes `gh` (`gh auth status` meldet je Host das aktive Konto und endet bei Problemen mit Exit-Code 1, https://cli.github.com/manual/gh_auth_status) und Schreibrecht im Repo: `gh repo view <owner/repo> --json viewerPermission,defaultBranchRef` liefert beides in einem Aufruf, `viewerPermission` muss `WRITE`, `MAINTAIN` oder `ADMIN` sein (Felder laut https://cli.github.com/manual/gh_repo_view).

- **Klonen:** `gh repo clone <owner/repo> <verzeichnis>` — nimmt `OWNER/REPO` oder eine URL, klont ins genannte Verzeichnis und wählt das Git-Protokoll aus der `gh`-Konfiguration, sodass derselbe Zugang später den Push trägt (https://cli.github.com/manual/gh_repo_clone).
- **Inventar:** `gh pr list --repo <owner/repo> --state open --limit 500 --json number,title,headRefName,baseRefName,isDraft,mergeable,reviewDecision,statusCheckRollup,author,url,updatedAt`, einmal mit `--search 'author:app/renovate'` und einmal ohne Suche zum Filtern nach dem Branchpräfix. `--limit` ist nötig, weil der Standard 30 ist und die Liste stillschweigend kappt; die Felder sind alle dokumentiert (https://cli.github.com/manual/gh_pr_list). `body` gehört nicht in die Liste — siehe Abschnitt B zur Größe.
- **Body je PR:** `gh pr view <n> --repo <owner/repo> --json body --jq .body > <datei>`; `headRefOid`, `reviews` und `reviewDecision` kommen vom selben Befehl (https://cli.github.com/manual/gh_pr_view).
- **Diff und Checks:** `gh pr diff <n> --repo <owner/repo>` zeigt den Diff des PRs, mit `--name-only` nur die geänderten Pfade — das genügt für die Frage, ob Manifeste, nur Locks, Dockerfiles oder Workflows betroffen sind (https://cli.github.com/manual/gh_pr_diff); `gh pr checks <n> --repo <owner/repo>` den CI-Stand je Check, mit Exit-Code 8 bei noch laufenden Checks (https://cli.github.com/manual/gh_pr_checks). Für die Klassifikation reicht der lokale Diff im Klon, `git diff origin/<basis>...origin/<head> -- <manifeste>`.
- **Eigene Approval auf dem aktuellen Head?** `gh api repos/<owner>/<repo>/pulls/<n>/reviews --paginate --jq '.[] | select(.state=="APPROVED") | {user: .user.login, commit: .commit_id}'` gegen `gh pr view <n> --json headRefOid --jq .headRefOid`. Der Umweg über die REST-API ist nötig, weil das `reviews`-Feld von `gh pr view` den Commit nicht trägt, auf den sich eine Review bezieht; die REST-Antwort führt ihn als `commit_id` und den Reviewstatus als `state`, `APPROVED` für eine Genehmigung (https://docs.github.com/en/rest/pulls/reviews, `gh api` mit `--jq` und `--paginate` laut https://cli.github.com/manual/gh_api).
- **Approve:** `gh pr review <n> --repo <owner/repo> --approve --body-file <datei>` — `--approve` markiert den PR als genehmigt, `--body-file` liest den Text aus einer Datei (https://cli.github.com/manual/gh_pr_review).

## E — Was Renovate tut, wenn jemand anderes pusht

Drei Sätze aus der Doku (https://docs.renovatebot.com/updating-rebasing/) tragen den ganzen Umgang mit Anpassungs-Commits:

1. „If you push a new commit to a Renovate branch, for example to fix your code so the tests pass, then Renovate stops all updates of that branch." — Nach dem ersten fremden Commit ist der PR eingefroren: keine neue Version, kein Rebase auf die bewegte Basis. Deshalb gehört ein Anpassungs-Commit nur auf PRs, die zeitnah gemergt werden, und der Approval-Text sagt, dass er da ist.
2. „Do _not_ amend Renovate's commits, because Renovate will rebase over your amended commit." — Ein eigener Commit obendrauf, nie ein Amend des Renovate-Commits.
3. „You can request that Renovate rebase a PR by selecting the rebase/retry checkbox" und „If you apply a rebase label then Renovate will regenerate its commit for the branch, even if the branch has been modified." — Checkbox (Abschnitt B) oder Label (`rebaseLabel`, Standard `rebase`) bauen den Branch neu, und fremde Commits sind dann weg. Darum steht dieser Satz im Approval-Text, und darum ist die Checkbox für einen PR mit Anpassung ein Rückschritt, kein Werkzeug.

Dazu der Hintergrund, warum ein Push abgewiesen werden kann: `rebaseWhen` (Standard `auto`, Werte `auto`, `never`, `conflicted`, `behind-base-branch`, `automerging`, https://docs.renovatebot.com/configuration-options/#rebasewhen) lässt Renovate den Branch neu aufsetzen, solange noch kein fremder Commit darauf liegt — etwa weil die Basis sich bewegt hat oder das Repo „Require branches to be up to date before merging" verlangt. Zwischen Klon und Push kann das passieren; dann ist `origin/<head>` ein anderer Commit, und der eigene Push muss nach `git fetch` auf den neuen Stand gesetzt werden. Force-Push ist nie die Antwort: Er würde Renovates neuen Stand überschreiben.

## F — Wann GitHub eine Approval zählt

- **Eigene PRs nie:** „Pull request authors cannot approve their own pull requests." (https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/approving-a-pull-request-with-required-reviews). Renovate ist der Autor, der Skill nicht — Pushen auf den Branch macht einen nicht zum Autor.
- **Nach eigenem Push eventuell nicht:** Die Branchregel „Require approval of the most recent reviewable push" verlangt „approval from someone other than the person who pushed it" (https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches). Hat der Skill den Anpassungs-Commit gepusht, zählt seine eigene Approval unter dieser Regel nicht.
- **Nach einem späteren Push eventuell nicht mehr:** „Dismiss stale pull request approvals when new commits are pushed" verwirft die Approval, sobald „a code-modifying commit is pushed to the branch of an approved pull request" (dieselben beiden Seiten). Deshalb kommt der Push vor der Approval, nie danach.
- **Ablesen:** `reviewDecision` kennt laut GraphQL-Schema drei Werte — `APPROVED` („has received an approving review"), `CHANGES_REQUESTED`, `REVIEW_REQUIRED` („A review is required before the pull request can be merged") — und ist nullbar (https://docs.github.com/en/graphql/reference/pulls): Ohne konfigurierte Review-Pflicht bleibt das Feld leer, und das heißt nur, dass keine Pflicht besteht, nicht, dass die Approval fehlt. `REVIEW_REQUIRED` trotz eigener Approval in `reviews` heißt dagegen: Die Regel aus dem zweiten Punkt greift, ein zweiter Mensch muss approven. Beides steht im Bericht, keines davon löst der Skill durch eine zweite Approval.
