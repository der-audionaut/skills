# Renovate PRs

How to recognize a Renovate PR, how it is built, which kinds exist and which of them `tool-dep-update-check` can check — plus the `gh` commands the skill uses to read and write, and the two rule sets that carry every decision about push and approve: what Renovate does with a branch someone else has touched, and when GitHub counts an approval. Every statement about behavior carries its source; the templates for branch and title come from Renovate's options source file (`lib/config/options/index.ts` on `main`, as of October 2026), because the docs show the same values only scattered across a very long page.

---

## A — Recognition

**The author.** The Mend Renovate GitHub App account appears in PR lists as `renovate[bot]`; GitHub searches filter app accounts with `author:app/<name>`, so `author:app/renovate` — the search docs describe the qualifier as "finds issues and pull requests created by a certain user or integration account" and give `author:app/robot` as the form for integration accounts (https://docs.github.com/en/search-github/searching-on-github/searching-issues-and-pull-requests). A self-hosted Renovate runs under any account, often a technical user without the `[bot]` suffix; then the author filter does not apply, and the second recognition carries alone.

**The branch.** Every Renovate branch starts with `branchPrefix`, default `renovate/`, "Prefix to use for all branch names" (https://docs.renovatebot.com/configuration-options/#branchprefix). After it comes `branchTopic`, by default `{{{depNameSanitized}}}-{{{newMajor}}}` plus `.x`, with the minor in between for separated patches, and the suffix `-lockfile` for a pure lock update (https://docs.renovatebot.com/configuration-options/#branchtopic). This yields `renovate/lodash-4.x`, `renovate/lodash-4.x-lockfile`, for groups `renovate/<groupSlug>` (`group.branchTopic` is `{{{groupSlug}}}`), for lockfile maintenance `renovate/lock-file-maintenance`, for Docker digest pins `renovate/digests-pin`, for rollbacks `…-rollback`, for replacements `…-replacement` and for security PRs `renovate/<datasource>-<dep>-vulnerability`. Whoever changed the prefix did so in the repo's Renovate configuration — it lives in `renovate.json`, `renovate.jsonc`, `renovate.json5`, `.github/renovate.json`, `.github/renovate.jsonc`, `.github/renovate.json5`, `.gitlab/renovate.json`, `.gitlab/renovate.jsonc`, `.gitlab/renovate.json5`, `.renovaterc`, `.renovaterc.json`, `.renovaterc.jsonc`, `.renovaterc.json5` or `package.json` (there under the key `renovate`) — according to the list `configFileNames` in Renovate's source code (https://github.com/renovatebot/renovate/blob/main/lib/config/app-strings.ts); the docs only say that `renovate.json` is the default and that with several files the first one found wins (https://docs.renovatebot.com/config-overview/). Read the file once, pull out `branchPrefix` and `additionalBranchPrefix`, otherwise assume `renovate/`.

**Why both.** Renovate itself uses branch name and PR title "like a cache key" (https://docs.renovatebot.com/key-concepts/pull-requests/): a PR belongs to Renovate if branch and title match its templates. The union of author filter and branch prefix finds both modes of operation — app and self-hosted —, and a PR found only via the prefix gets a note in the report that its author is not the Renovate app account.

## B — Anatomy

**The title** is the branch's commit message and is assembled from three templates (https://docs.renovatebot.com/configuration-options/#commitmessageaction, `#commitmessagetopic`, `#commitmessageextra`): `commitMessageAction` (default `Update`), `commitMessageTopic` (default `dependency {{depName}}`) and `commitMessageExtra` (default `to <version>` — for majors only the major number, for digests the short digest). From this:

- `Update dependency lodash to v4.17.21` — one package, one version.
- `Update dependency lodash to v5` — a major; the docs warn that titles without a full version, like `Update react (major)`, can mean several updates (https://docs.renovatebot.com/key-concepts/pull-requests/).
- `chore(deps): update dependency lodash to v4.17.21` — with `semanticCommits` (default `auto`: on if the repo's history shows conventional commits, https://docs.renovatebot.com/configuration-options/#semanticcommits), type `chore`, scope `deps`, and `commitMessageLowerCase` `auto` lowercases the rest.
- `Update all non-major dependencies` or another `groupName` — a group PR; `group.commitMessageTopic` is `{{{groupName}}}`.
- `Lock file maintenance` — `lockFileMaintenance.commitMessageAction`, without topic and extra.
- `Pin dependencies` — `pin.commitMessageAction` `Pin` with topic `dependencies`, group `Pin Dependencies`.
- `Update node Docker tag to v22` and `Update node:22 Docker digest to abc1234` — the Docker datasource sets `commitMessageTopic` to `{{{depName}}} Docker tag` or `… Docker digest` respectively (https://github.com/renovatebot/renovate/blob/main/lib/modules/datasource/docker/index.ts); `Pin Docker digests` is the pin group.
- `Roll back dependency lodash to v4.17.20`, `Replace dependency request with …`, `Update dependency lodash to v4.17.21 [SECURITY]` — rollback, replacement, security PR (suffix from `vulnerabilityAlerts.commitMessageSuffix`).

GitHub Actions updates carry the generic topic — the manager brings no title template of its own (https://github.com/renovatebot/renovate/blob/main/lib/modules/manager/github-actions/index.ts) — as long as no preset overrides it; for them, do not rely on the title but on the changed files under `.github/workflows/` (section C).

**The body** is built from fixed building blocks in a fixed order (https://github.com/renovatebot/renovate/blob/main/lib/workers/repository/update/pr/body/index.ts): header, update table, notes, release notes, configuration description, controls, footer. What the skill needs:

- **The table** starts with the line `This PR contains the following updates:` and has one row per update; the columns are `prBodyColumns`, default `Package`, `Type`, `Update`, `Change`, `Pending`, empty columns are dropped (https://docs.renovatebot.com/configuration-options/#prbodycolumns). The `Change` column is defined as `` `{{{displayFrom}}}` → `{{{displayTo}}}` `` (https://docs.renovatebot.com/configuration-options/#prbodydefinitions) — with the arrow `→` (U+2192); older Renovate versions and many still-open PRs write `->`. Whoever greps the rows out of the body searches for both. For lockfile maintenance, `Change` holds only `All locks refreshed`. The columns `Age`, `Adoption`, `Passing` and `Confidence` are optional definitions with Mend badges that some configurations turn on.
- **The release notes** sit collapsed below the table, because `fetchChangeLogs` is `pr` by default (https://docs.renovatebot.com/configuration-options/#fetchchangelogs). They make the body large — ten to fifty kilobytes are normal — and they are not the skill's source: `tool-dep-update-check` reads changelogs itself and completely.
- **The rebase checkbox** is the line `- [ ] <!-- rebase-check -->If you want to rebase/retry this PR, check this box` (https://github.com/renovatebot/renovate/blob/main/lib/workers/repository/update/pr/body/controls.ts). It is the control that makes Renovate rebuild the branch — and that discards every foreign commit, see section E.
- **The "Immortal" note** (`This PR will be recreated if closed unmerged`) appears on PRs that Renovate recreates after closing (https://docs.renovatebot.com/key-concepts/pull-requests/). It is irrelevant to the check; it only explains why closing is not a solution.

## C — PR kinds and checkability

`tool-dep-update-check` checks exactly one pair: one package, one source and one target version, in an ecosystem its reference knows (npm, Composer, Maven, Gradle, pip and relatives, Cargo, Go, Bundler, NuGet — `skills/tool-dep-update-check/references/ecosystems.md`). What counts is not the title but the diff of the PR branch against its base, restricted to manifest and lock files; the body table is the counter-check.

- **One package, manifest and lock changed** — checkable. The pair is in the manifest diff; the table row must say the same.
- **One package, only lock changed** (branch with `-lockfile`, section A) — checkable. The target lies within the existing constraint; `tool-dep-update-check` calls this a pure lock update in its report (`skills/tool-dep-update-check/SKILL.md`, section 2, the paragraph on constraint versus lock). The pair comes from the lock diff.
- **Group PR** — checkable, one pair per table row, each on its own. The PR can only be approved if every pair is possible; splitting the group is Renovate configuration (`groupName`, `separateMinorPatch`), not the skill's business.
- **Lockfile maintenance** — not checkable. All locks are refreshed, there is no pair, and the number of moved packages is arbitrary. Skipped, with reason.
- **Pin PR** — not checkable, because there is nothing to check: the manifest switches from a range to the version the lock already holds; source and target are equal. Skipped, with reason — the decision whether the project wants to pin is configuration.
- **Docker tag, Docker digest, digest pin** — not checkable: not an ecosystem of the check, and the checking skill's trial run (install, build, tests) says nothing about a base image. Skipped.
- **GitHub Actions** (files under `.github/workflows/`, version or digest update of an action) — not checkable, for the same reason. Skipped.
- **Rollback** — not checkable: a downgrade, for which `tool-dep-update-check` asks whether it is meant that way (`skills/tool-dep-update-check/SKILL.md`, section 1). Skipped, with the note that a rollback is a different task.
- **Replacement** (`Replace dependency …`) — not checkable: a different package, not a version jump. Skipped.
- **Security PR** (`[SECURITY]`) — checkable like a normal package PR; the suffix changes nothing about pair and diff. As for the alert itself — whether the target version closes it —, that is the business of the team skill `update-packages`, not this one.

A PR whose manifest diff and table contradict each other — different package, different version — is not checkable and is reported as such; guessing which side is right is not a check.

## D — The `gh` commands

All commands need a logged-in `gh` (`gh auth status` reports the active account per host and exits with code 1 on problems, https://cli.github.com/manual/gh_auth_status) and write permission on the repo: `gh repo view <owner/repo> --json viewerPermission,defaultBranchRef` delivers both in one call, `viewerPermission` must be `WRITE`, `MAINTAIN` or `ADMIN` (fields per https://cli.github.com/manual/gh_repo_view).

- **Clone:** `gh repo clone <owner/repo> <directory>` — takes `OWNER/REPO` or a URL, clones into the named directory and picks the Git protocol from the `gh` configuration, so the same access later carries the push (https://cli.github.com/manual/gh_repo_clone).
- **Inventory:** `gh pr list --repo <owner/repo> --state open --limit 500 --json number,title,headRefName,baseRefName,isDraft,mergeable,reviewDecision,statusCheckRollup,author,url,updatedAt`, once with `--search 'author:app/renovate'` and once without search, for filtering by branch prefix. `--limit` is necessary because the default is 30 and silently truncates the list; the fields are all documented (https://cli.github.com/manual/gh_pr_list). `body` does not belong in the list — see section B on size.
- **Body per PR:** `gh pr view <n> --repo <owner/repo> --json body --jq .body > <file>`; `headRefOid`, `reviews` and `reviewDecision` come from the same command (https://cli.github.com/manual/gh_pr_view).
- **Diff and checks:** `gh pr diff <n> --repo <owner/repo>` shows the PR's diff, with `--name-only` only the changed paths — that is enough for the question whether manifests, only locks, Dockerfiles or workflows are affected (https://cli.github.com/manual/gh_pr_diff); `gh pr checks <n> --repo <owner/repo>` shows the CI state per check, with exit code 8 while checks are still running (https://cli.github.com/manual/gh_pr_checks). For classification the local diff in the clone is enough, `git diff origin/<base>...origin/<head> -- <manifests>`.
- **Own approval on the current head?** `gh api repos/<owner>/<repo>/pulls/<n>/reviews --paginate --jq '.[] | select(.state=="APPROVED") | {user: .user.login, commit: .commit_id}'` against `gh pr view <n> --json headRefOid --jq .headRefOid`. The detour via the REST API is necessary because the `reviews` field of `gh pr view` does not carry the commit a review refers to; the REST response lists it as `commit_id` and the review state as `state`, `APPROVED` for an approval (https://docs.github.com/en/rest/pulls/reviews, `gh api` with `--jq` and `--paginate` per https://cli.github.com/manual/gh_api).
- **Approve:** `gh pr review <n> --repo <owner/repo> --approve --body-file <file>` — `--approve` marks the PR as approved, `--body-file` reads the text from a file (https://cli.github.com/manual/gh_pr_review).

## E — What Renovate does when someone else pushes

Three sentences from the docs (https://docs.renovatebot.com/updating-rebasing/) carry the whole handling of adaptation commits:

1. "If you push a new commit to a Renovate branch, for example to fix your code so the tests pass, then Renovate stops all updates of that branch." — After the first foreign commit the PR is frozen: no new version, no rebase onto the moving base. That is why an adaptation commit only belongs on PRs that get merged soon, and the approval text says that it is there.
2. "Do _not_ amend Renovate's commits, because Renovate will rebase over your amended commit." — Your own commit on top, never an amend of the Renovate commit.
3. "You can request that Renovate rebase a PR by selecting the rebase/retry checkbox" and "If you apply a rebase label then Renovate will regenerate its commit for the branch, even if the branch has been modified." — Checkbox (section B) or label (`rebaseLabel`, default `rebase`) rebuild the branch, and foreign commits are then gone. That is why this sentence is in the approval text, and why the checkbox is a step backwards for a PR with an adaptation, not a tool.

Plus the background on why a push can be rejected: `rebaseWhen` (default `auto`, values `auto`, `never`, `conflicted`, `behind-base-branch`, `automerging`, https://docs.renovatebot.com/configuration-options/#rebasewhen) lets Renovate rebuild the branch as long as no foreign commit sits on it yet — for instance because the base has moved or the repo requires "Require branches to be up to date before merging". That can happen between clone and push; then `origin/<head>` is a different commit, and your own push must be put onto the new state after `git fetch`. Force-push is never the answer: it would overwrite Renovate's new state.

## F — When GitHub counts an approval

- **Own PRs never:** "Pull request authors cannot approve their own pull requests." (https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/approving-a-pull-request-with-required-reviews). Renovate is the author, the skill is not — pushing to the branch does not make you the author.
- **Possibly not after your own push:** The branch rule "Require approval of the most recent reviewable push" requires "approval from someone other than the person who pushed it" (https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches). If the skill pushed the adaptation commit, its own approval does not count under this rule.
- **Possibly no longer after a later push:** "Dismiss stale pull request approvals when new commits are pushed" discards the approval as soon as "a code-modifying commit is pushed to the branch of an approved pull request" (the same two pages). That is why the push comes before the approval, never after.
- **Reading it:** According to the GraphQL schema, `reviewDecision` has three values — `APPROVED` ("has received an approving review"), `CHANGES_REQUESTED`, `REVIEW_REQUIRED` ("A review is required before the pull request can be merged") — and is nullable (https://docs.github.com/en/graphql/reference/pulls): without a configured review requirement the field stays empty, and that only means there is no requirement, not that the approval is missing. `REVIEW_REQUIRED` despite an own approval in `reviews`, on the other hand, means: the rule from the second point applies, a second human must approve. Both go into the report; the skill resolves neither with a second approval.
